WhichToUse 产品结构原型

用来在动手写产品代码之前把结构吵清楚：有哪些页面、每页放什么块、每块的数据从哪来。 这里的东西不发布，改起来没有代价 —— 请直接对具体块提意见。

每页右上角有「显示数据来源」开关

打开后每个块会显示它的数据出处，颜色即证据强度：

你的判断 · 护城河 硬数据 · 公开 API 可算 人工核实 · 会过期 软信号 · 证据较弱
P1 首页

要验证：撤掉裸 GitHub Trending，换成「本周值得一看」（每条带你的一句判断）， 再加一张跨分类的「稳妥之选 vs 新王候选」总表。

P2 分类页 — 主战场

要验证：顶部两张稳妥/新王对置卡；中部维持现有双轨排行； 下部新增「价格与短板一览」横向表（护城河可视化）；末尾是筛过的新品雷达。

P3 产品详情页 — 优先级最高

要验证：从抽屉改成独立 URL。现在详情是 #item=app:1， 搜索引擎和 AI 引擎完全看不到你最有价值的内容。这一项不需要任何新数据源。

P4 对比页 — 用已有数据换高意图流量

要验证：/vs/a-vs-b 能否用已有数据自动生成。 「X vs Y」是转化意图最强的词之一，而成本接近零。

建议的落地顺序
  1. P3 详情独立页 —— 解锁已有内容的 SEO/GEO 价值，不需要新数据
  2. 价格新鲜度标记（核实于 7月23日）—— 把护城河变成可见的信任
  3. P4 对比页 —— 已有数据换高意图流量
  4. 稳妥/新王 —— 要接外部 API，工作量最大，放最后
  5. 首页撤掉裸 trending
一个必须设计进去的不对称： OSS 侧有 npm / Homebrew / PyPI 的真实采纳量（硬数据）， SaaS 侧拿不到下载量，只能用存在年限、被测评收录频率这类软信号。 两条轨道不能用同一套话术假装同样严谨 —— 这恰恰是你的诚实定位能吃到的红利。
