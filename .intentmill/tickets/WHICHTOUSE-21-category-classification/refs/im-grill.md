# IntentMill Grill

## Blocking Decisions

1. id: D1-assignment-shape
   question: When a candidate returned by category A's search judges as belonging to category B, is it written to B (candidates become global and are filed wherever they belong), or is the judgement only ever "confirm A or discard" (a candidate can never leave the category that found it)?
   recommendation: Confirm-or-discard. The ticket's own wording is "judge against all 25, discard when the judgement is insufficient", and discard is the only branch it names; reassignment additionally breaks the evidence contract, because `evidence.sources` records a per-source rank ("GitHub (stars) #5") that was earned inside another category's ranked list and would render on B's card as if B's search had produced it. Confirm-or-discard also keeps the per-category loop in `app/jobs/refresh.mjs` intact, which is the smaller surgery. The cost is real and should be accepted knowingly: a genuinely good tool found by the wrong query is thrown away rather than filed correctly, and it can only reappear when a search for its own category finds it.
   final_decision: TBD

2. id: D2-corroboration-model
   question: What replaces `selfPlacing: true` on `github-skills` and `producthunt` — a confident category judgement standing in for the missing second origin, counting GitHub's topic-search and keyword-search as distinct corroboration methods, or keeping the bypass only for the topic-classified half of `github-skills` and removing it from Product Hunt?
   recommendation: Let a confident assignment substitute for the second origin, and narrow `selfPlacing` from "this source may place alone" to "this source may place alone when the candidate also clears the assignment bar". That is what the existing `sources.json` note already argues on precision grounds ("a topic is the author's own classification, so precision is high enough to place a listing without a second origin"), and it is the only formulation that survives the ticket's own constraint: all skill sources share the `github` origin, and Product Hunt is the sole `saas` discovery source (`specs/content-in-db.md` §3.3a/§3.4), so any absolute two-origin rule empties both tracks. Counting `topic:` and keyword searches as two "origins" is rejected in the recommendation: they are the same site and can agree for the same wrong reason, which is exactly the failure `origin` was introduced to prevent.
   final_decision: TBD

3. id: D3-strictness-arbitration
   question: When the confidence bar that satisfies AC3 ("at most one wrong entry per sampled list") would leave a category's emerging list empty or near-empty — which the constraints forbid — which side gives: does the list go short/empty honestly, or does the category keep its weakest surviving candidates, and may the bar be calibrated per category rather than globally?
   recommendation: Honesty wins on the row (never invent a placement to fill a slot), and the bar stays a single global rule rather than 25 hand-tuned ones — a per-category threshold is untestable against a 100-row baseline and becomes a second classifier hidden in config, which is the failure mode `sources.json` already accumulated with four parallel per-category vocabularies. Where a category genuinely comes up short, the answer is the UI treatment in D7, not a lower bar. This decision needs a user answer because the two ticket constraints ("≤1 wrong per list" and "no emptied lists") can conflict on real data and only the owner can say which one yields.
   final_decision: TBD

4. id: D4-classification-input-budget
   question: May the assignment stage spend extra API calls to read more about a candidate — a GitHub `core`-bucket call per candidate for README/repository metadata, and a wider Product Hunt query pulling `description` and per-post `topics` — or must it judge only on what the current responses already carry (repo name, description, topics; PH name and tagline)?
   recommendation: Start with the free text and no extra calls. Repository search responses already include `topics` (verified live: `topic:agent-skills` returns populated `topics`), which is the highest-precision signal available; the PH query change is cheap within the documented 6250-complexity/15-min quota and should be taken because a bare tagline is the thinnest input in the set. Answer D11 alongside this one: neither GitHub `topics` nor a widened Product Hunt field exists in any column of `listings`, so leaning on either decides how — and for which tracks — the existing 287 rows can be re-judged. Any widened Product Hunt fields are classification input only and are not persisted — see the guardrail, since Product Hunt data has a commercial-use redline. Hold README/metadata enrichment back as a measured fallback: it spends the `core` bucket (5000/h — it does not compete with the 30/min `search` bucket), but ~1000 calls lengthen a run already spending ~4 minutes in serialised search throttling, and the repo's own helpers for those calls (`githubJson`/`githubReadme` in `app/src/lib/github-trending.ts`) swallow errors and return `null`/`''`, so a degraded run would look like a quiet run. Answering this also settles the Hacker News consequence: HN entries are built with `description: null`, so under "no extra calls" every HN-discovered repo is discarded and HN reverts to pure corroboration — which matches its documented role but does narrow `oss` discovery at the same moment D2 tightens it.
   final_decision: TBD

5. id: D5-autonomy-of-the-judgement
   question: Must the daily unattended job be self-sufficient (a deterministic rule plus versioned config decides everything), or may the shipped design lean on a periodic offline agent-assisted pass — the `app/scripts/describe-emerging.mjs` pattern, where a script emits a prompt, an agent answers, and a validator writes — to curate the vocabulary or adjudicate the candidates the rule cannot decide?
   recommendation: Ship a self-sufficient deterministic rule for the daily job, and allow an offline pass only as a vocabulary-improvement tool whose output is committed to `app/src/content/sources.json` — never as a runtime gate. No model or key exists in the job environment (`GITHUB_TOKEN`, `PRODUCTHUNT_TOKEN`, `DATABASE_URL` only) and `engineering-rules.md` forbids adding one, so a runtime judgement call is not available; and a design where the daily job waits for a human leaves candidates in limbo between passes. The user's answer matters because the alternative — accepting recurring human/agent labour as part of emerging placement — is an operating-model choice, not a coding one.
   final_decision: TBD

6. id: D6-withdrawal-of-the-misfiled-rows
   question: The ~100 rows already labelled misfiled are currently ranked and rendering. When the new rule runs, they lose their rank and disappear immediately, and their `/c/{slug}/{item}` detail URLs start returning 404 — is that immediate withdrawal the accepted behaviour, or must those rows keep rendering until something replaces them?
   recommendation: Accept immediate withdrawal. The job never deletes rows — it nulls `rank` and rewrites placements — so `best_for = ''` and the row itself survive intact and the evaluation baseline the ticket protects is not touched; only visibility changes. Keeping known-wrong entries on the page to avoid a gap would contradict `goal.md`'s honesty claim and the "no pay-to-rank filler" posture. The user needs to confirm because ~100 previously live product URLs begin 404-ing at the first run after deploy (`c_.$slug.$item.tsx` throws `notFound()`), which is an SEO and inbound-link consequence, and because it is the visible half of the ticket's acceptance measurement.
   final_decision: TBD

7. id: D7-what-the-site-says-when-a-list-thins
   question: When honest discarding leaves an Emerging band, a whole track, or a whole category empty, what does the site show, and which of the knock-on surfaces are accepted as-is? Today the band is silently omitted (`Standing` returns `null`); an empty track shows the generic "Nothing here yet / Nothing on this route has made the shortlist"; the category is greyed out and unclickable in the rail on every page (`app-frame.tsx`, `isDisabled={!category.ready}`); it can drop out of the four home-page featured leaderboards (`getHomeFeatured`, app track, `items.length >= 5`); the home page's "N areas of work" figure is `ready.length`, so it ticks down while `app/src/theme/brand.json` and `app/public/site.webmanifest` keep claiming "25 areas of work" in the site description; and every withdrawn row also disappears from site search, since `searchEntries` is built only from ranked rows.
   recommendation: Name the absence in one line inside the existing card rather than leaving a silent gap; leave the rail, the featured cards, the search index and the counted "N areas of work" figure to follow from `ready` as they already do; and leave the "25 areas of work" description strings alone, since 25 is the size of the taxonomy and stays true even when a category has nothing ranked — a claim about coverage, not about today's rows. GitHub's topic and search surfaces state "no repositories matched" rather than rendering a quietly shorter list, and this repo has already taken the same position in `specs/content-in-db.md` §3.1a — that the visible difference between "ranked by aggregation" and "we sat down with this one" is the product's whole pitch, which is why `reviewed_at` and `signals` exist. A band that vanishes tells the reader the field is thin when the truth is that we discarded what we found. Any such line must use the existing Astryx `EmptyState`/`Text` components and `app/src/theme/neutralTheme.ts` tokens — there is no `DESIGN.md` in this repo, it was deleted with the `demo/` reference — and must stay one line, because `goal.md` binds the UI to compact. The wording itself and whether the rail/featured behaviour is acceptable are product calls only the owner can make.
   final_decision: TBD

Leaving it is the one option to avoid: the site's differentiator is honesty about evidence, and this tooltip is a direct statement about how the row got there. The exact sentence is a copy decision for the owner; it must remain a single `Text`/tooltip line under the existing components, not a new surface.

That keeps the measurement reproducible across runs and reviewers, keeps the acceptance evidence out of a live-connection-only path, and avoids the implementation phase reaching production without the tool the engineering rules route database work through. 10. id: D10-evaluation-artefact-boundary

11. id: D11-rule-inputs-vs-the-measurable-baseline
    question: The inputs D4 leans on are not stored anywhere. `listings` has no topics column (`name`, `owner`, `track`, `homepage`, `repo_full_name`, `package_name`, `source_description` only), and a widened Product Hunt query's `description`/`topics` would be equally unstored — guardrail-forbidden from being persisted. Re-fetching recovers the GitHub inputs for `oss`/`skill` rows via `repo_full_name`, but **not** for `saas` rows: `refresh.mjs` sets `repoFullName: repoOf(node.website)` and types exactly the rows where that is null as `track: 'saas'`, so those rows carry no repo handle to re-fetch, and there is no investigated Product Hunt lookup-by-homepage. So: is the assignment rule allowed to use inputs the 287-row re-judgement cannot reproduce, and if so, does the acceptance measurement cover the `saas` track or exclude it?
    recommendation: Split the answer by track rather than choosing one rule for both. Let the shipped rule use GitHub `topics` freely for `oss` and `skill` — that is the author's own classification and the highest-precision evidence available, and dropping it to suit a one-off measurement would trade the fix for the metric; those rows carry `repo_full_name`, so the re-judgement recovers the same inputs with one `core`-bucket call each (well inside 5000/hour). For `saas`, hold the rule to `name` plus the stored `source_description` — which is exactly the Product Hunt tagline captured at discovery and never overwritten — so the saas subset stays decidable from a fixture with the shipped rule intact. Be aware that this cuts against D4's own recommendation: taking this split means declining the Product Hunt widening for classification purposes, because any field it adds is unstored, unpersistable under the guardrail, and therefore unreproducible at measurement time. If the widening is wanted more than the faithful measurement, take the alternative below instead. The alternative worth stating because it may be preferred: widen the PH query anyway, accept that the saas track cannot be re-judged faithfully, and qualify the acceptance number as covering `oss`/`skill` only. You need to answer because it decides both the rule's design ceiling and what "≥80 of 100 no longer in their original category" actually attests to — and because the saas track is where classification is hardest (six categories collapsed onto the `productivity` topic, Product Hunt the only saas discovery source).

12. id: D12-coverage-of-the-two-rewired-seams
    question: The two seams this ticket rewires — the per-source dispatch and the emerging placement guard in `app/jobs/refresh.mjs` — sit in fetch-touching job code with no automated coverage today and no fetch-stubbing pattern anywhere in the repo (one test exists, a pure HTML parser). Is it accepted that those seams ship verified only by a live `--dry` run plus unit tests of the extracted pure rule, or must this ticket also build a stub harness so the wiring itself is tested?
    recommendation: Accept `--dry` plus pure-rule unit tests for this ticket. The extracted assignment rule is where the judgement lives and is fully unit-testable under `app/vitest.config.ts`'s `src/**/*.test.ts`; the seams around it are wiring, and inventing a fetch-mocking layer for a 763-line job with no exports is a larger change than the ticket, made in the same commit as the behaviour change. The risk being accepted is specific and worth stating rather than burying: this job has already shipped two silent-output failures (the `"ai"` Product Hunt topic that returned zero rows for 25 categories without an error, and readme-scoped search ranking `sindresorhus/awesome` first), and a wiring bug in a stage whose job is to discard candidates looks exactly like a quiet day at the sources — which is why the discard-reporting default matters more than usual here. Your answer is a quality/release-risk tradeoff, not an implementation detail.

## Recommended Defaults

- Replace `hay.includes(w)` with word-boundary matching, reusing the technique already in `app/src/lib/github-trending-enrichment.ts` (`CATEGORY_RULES`: ordered, specific-first, word-boundary regexes over name/description/topics) — but not its `?? 'Coding'` fallback, which is the exact behaviour the ticket forbids. This is what kills `resume`/"resumable" and `sql`/"SQLite".
- Keep the classification vocabulary in `app/src/content/sources.json` next to `skillClassify` rather than introducing a new config file: that file is the versioned allowlist by design ("adding a source is a reviewed commit, never a silent change", `specs/content-in-db.md` §3.2).
- Put the pure assignment rule in a module under `app/src/lib/` so `app/vitest.config.ts` (`include: ['src/**/*.test.ts']`) can reach it; `app/scripts/build-jobs.mjs` bundles the job with esbuild and resolves such an import with no config change. `app/jobs/refresh.mjs` exports nothing and calls `main()` at top level, so it cannot be imported by a test as it stands.
- Carry `topics` through the entry mapping in `githubSearch` and `githubSkillSearch`; today both discard it and only `sweepSkills` keeps the raw repo objects, which is why only the sweep half can classify at all.
- Apply the assignment stage to the `githubSkillSearch` half of `github-skills` too — it is currently unioned in unclassified under a `selfPlacing` source, which is how `topic:agent-skills support` writes Customer Support rows alone.
- Withdraw a row by leaving `rank = null`, never by deleting it: that is the job's existing behaviour and it is what preserves `best_for = ''` on the 100 labelled rows.
- Never re-file or withdraw a row with `reviewed_at != null`; those are placed by the reviewed-rows branch and their category is human-owned per the ticket constraint.
- Report what the run discarded, and why, next to `summary.sourceErrors`. This job has already shipped two failures that produced plausible output instead of an error (the `query.split(' ')[0]` → `"ai"` Product Hunt bug that returned zero rows for 25 categories silently, and readme-scoped search ranking `sindresorhus/awesome` first); a stage whose whole job is to drop candidates must not be the third.
- Scope automated tests to the extracted pure rule rather than inventing a fetch-mocking layer: the repo has exactly one test (`app/src/lib/github-trending-parser.test.ts`, a pure parser) and no stub/mock pattern to follow, and `app/jobs/refresh.mjs` exports nothing and runs `main()` at import time. Whatever D12 settles about the seams, the rule itself is covered this way.
- Unit tests pin the named regressions: `resume`/"resumable", `sql`/"SQLite", the single-word `skillQueries` collisions (`support`, `data`, `browser`, `pdf`, `image`), the six categories sharing the `productivity` Product Hunt topic, and the "not confident → dropped, no fallback category" path.
- If a classification outcome is persisted at all, put it in the existing machine-owned `evidence` jsonb; `ssot-schemas/db-schemas/whichtouse.sql` is the SSOT and changing it is a separate, deliberate act.
- Leave the `npm` source alone — it only re-ranks listings that already carry `package_name` and cannot create a row.
- `node --env-file=.env .output/jobs/refresh.mjs --dry --category <slug>` is the end-to-end check; `--dry` logs and skips the transaction, so it writes nothing. It is not access-free, though: it selects from `categories` and `listings` on the production schema and needs both source tokens, so it falls under D9 rather than around it.

- Rewriting `skillQueries` and `phTopics` themselves. The ticket names them as diagnosis, not as required work, and D1's assignment stage neutralises them by construction; revisit only if measurement shows the queries starve a category of correct candidates in the first place.
- The hard-coded `artificial-intelligence` Product Hunt fallback in `app/jobs/refresh.mjs`. Latent today — all 25 slugs have a `phTopics` entry — but it silently files a future 26th category under the most crowded topic.

- Azure Container Apps Job timeout and retry posture. Nothing in the repo records it; it matters only if D4 is answered in a way that lengthens the run materially beyond the current ~4 minutes of throttling.

- The stale evodocs modules are not rewritten as a side effect of this ticket.
